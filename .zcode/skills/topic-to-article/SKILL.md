# Topic → Article 流水线

一句话命中本技能后，按 Step 0 → Step 5 走。**不要跳步，不要边调研边写，不要替用户假设用途，不要自己发明笔记结构。**

## 前置：两个路径（开工前确认一次）

本技能依赖一个**外部笔记模板业务项目**（见「外部资源」节），开工前必须能解析出：

| 变量 | 含义 | 拿不到怎么办 |
|---|---|---|
| `$BLOG_ARTICLE_SKILL_DIR` | 模板项目根目录（外部依赖，不在本仓库：含 `prompts/` 与 `scripts/persist_summary.py`） | 问用户一次，不要猜路径、不要跳过 Step 3/4 |
| `$OBSIDIAN_VAULT` | 笔记最终落盘的真实 Obsidian 库目录 | 只在 Step 4 落盘时需要；用户说"先给我看稿"时可暂缺 |

值由平台注入，或从本技能目录的 `.env`（由 `.env.example` 生成）读取。**两个变量都拿不到时，本技能降级为"只调研不出稿"，须先告知用户。**

## 用户画像（已确认的偏好，2026-09-15）

- **用途不固定**，可能是自己搞懂 / 对外科普 / 表达观点 / 商业转化中的任意一种 → 每次必问，不许默认。
- **产物形态 = 复用模板项目的现成模板**，不是自造六段式。用哪个由 Agent 按选题性质 + 用户回答判断。
- **信源规则**：关键数据必须有可跳回的出处；观点性判断可宽松，但**具体数字绝不允许编**。

## 铁律

- **不替用户决定用途。** 用途错了，后面全白做。
- **不自己发明笔记结构。** 9 个现成模板是单一真源，选一个照着写；没一个合适的才用 `general`。
- **不编造信源。** 溯不到源的结论要么标"有观点认为"，要么删掉。
- **调研没过 Gate 不动笔。**
- **默认落本地 Obsidian**，飞书只在用户明确要求时写。
- 子技能靠 **CLI 命令 / 子 Agent** 驱动，不要指望连续触发多个 Skill（一次只能加载一个）。

## Step 0 · 强制澄清（不确认不开工）

一次问完，不要挤牙膏式多轮追问。三个问题：

1. **受众是谁？**（自己 / 同行 / 外行小白 / 潜在客户）
2. **要什么形态？**（结构化笔记 / 短帖 300–800 / 中篇 1500–2500 / 长文 3000+）
3. **这次的重点？**（搞懂原理 / 拿结论做决策 / 找素材做内容 / 挑毛病找反例）

**只有用户说"老规矩 / 照上次 / 你看着办"才可跳过**，此时取默认值：
受众=自己、形态=结构化笔记、重点=搞懂原理。

同一轮对话里已答过的，后续追加选题不必重复问，直接复用。

## Step 1 · 分路调研（强度按用途伸缩）

**先判断要不要跑两路**：

| 用途 | 调研强度 |
|------|----------|
| 自己搞懂 / 内化笔记 | 一路即可（事实路为主），不必跑 15 平台 |
| 对外发布 / 观点 / 商业 | 必须两路并行 |

**路线 A · 口碑与真实讨论**（用 `agent-reach`，对外向内容才跑）
1. 先跑 `agent-reach doctor --json`，看各平台 `active_backend` 再选命令组。
2. 目标：真实用户吐槽、案例、中文语境下的说法、平台差异。
3. 输出 ≤10 条要点，每条带平台 + 链接。

**路线 B · 硬事实考据**（按 `research` 技能规则派后台 agent）
1. 只认一手信源：官方文档、源码、RFC/标准、一手 API、论文、官方统计数据。
2. Medium / dev.to / 公众号二手解读 / "top 10" 列表 **不算信源**，只能当线索。
3. 产出带引用的 Markdown（每条结论可跳回出处）。

## Step 2 · 素材表（Gate，必过）

合并成一张表：

| 结论 | 出处 | 是否一手 | 用在哪段 |
|------|------|----------|

Gate 检查：
1. **出现的每个具体数字 / 事实**，是否都有可跳回的出处？没有 → 补或删。
2. 这条是**事实**还是**我的判断**？判断可以没有出处，但要写清楚是判断。
3. 有没有核心论断"只有自媒体在说"？有 → 降级为"有观点认为 / 据 XX 社区反馈"。
4. 与本次重点无关的好材料 → 扔掉，不要因为难得就塞进来。

**过不了就回去补调研，不要硬写。**

## Step 3 · 选模板 → 成文

### 3.1 读模板清单（每次必做，别凭记忆）

```bash
cd "$BLOG_ARTICLE_SKILL_DIR" && python -c "from prompts.templates import list_note_types; [print(t['key'],'|',t['name'],'|',t['desc']) for t in list_note_types()]"
```

9 个模板：`structured` / `key_points` / `case` / `opinion` / `interview` / `roundup` / `reading` / `dissection` / `general`。

### 3.2 Agent 判断用哪个（依据 = 选题性质 + Step 0 的回答）

**先按选题本身长什么样选**，这是主依据：

| 选题长这样 | 用这个 |
|---|---|
| 搞懂一个概念 / 方法论 / 技术原理 / 怎么做 | `structured` 结构化复盘 |
| 多个选项要横向比、选哪个 | `roundup` 盘点（维度×对象矩阵） |
| 有明确立场、要争、站队 | `opinion` 观点卡（正反双方 + 我的立场） |
| 某人 / 某公司怎么把一件事做成的 | `case` 案例拆解 |
| 拆一条爆款 / 一个账号为什么有效 | `dissection` 创作解剖（提炼结构模具） |
| 围绕一本书 | `reading` 读书笔记 |
| 听一场演讲 / 公开课 / 播客后的要点 | `key_points` 要点提炼 |
| 整理某个人的一问一答 | `interview` 访谈（原创选题极少用到） |
| 都不像 | `general` 通用兜底 |

**再用 Step 0 的回答校准**：
- 重点=「搞懂原理」→ 偏 `structured`；重点=「拿结论做决策」→ 偏 `roundup` / `opinion`。
- 受众=自己 → 允许术语密度高；受众=外行小白 → 模板里"术语卡 / 大白话解释"那些**按需模块从可选变必写**。
- 形态=短帖 → 只保留模板的核心必备模块，可选模块整块删（模板本身允许去水分，别硬凑）。

**两个以上沾边时**，问自己一句：**读者看完主要想带走什么？** 想带走"怎么做"→ structured；想带走"选哪个"→ roundup；想带走"我同不同意"→ opinion；想带走"它做对了啥我能抄"→ case / dissection。

**交叉验证（可选，判断拿不准时用）**：

```bash
cd "$BLOG_ARTICLE_SKILL_DIR" && python -c "from prompts.classify import classify_note_type; print(classify_note_type('<标题>','<正文前800字>'))"
```

这是关键词机械分类器，只作参考。**它跟你的判断冲突时，以你的判断为准**——它是为"总结已有素材"设计的，对原创选题的标题容易误判。

### 3.3 取完整 prompt 照着写（不要凭印象复述模板）

```bash
cd "$BLOG_ARTICLE_SKILL_DIR" && python -c "from prompts.templates import get_note_prompt; print(get_note_prompt('structured'))"
```

把 `structured` 换成 3.2 选中的 key。**prompt 有 6000+ 字符，必须用命令取全文，禁止凭记忆缩写。**

### 3.4 原创稿对模板的 4 条覆盖（模板是为"总结已有素材"写的，这里要改口径）

1. **「忠于原文 / 不篡改作者观点」→ 改为「忠于信源」**。没有单一原文，素材表就是你的"原文"；推断一律标「（笔记者推断）」，补充标「【补充】」。
2. **作者行 → 作者是用户本人**。来源链接 = 关键信源（有多条就在正文对应位置用 `[文字](url)` 内联，不要堆在开头）。
3. **字数参考值「源长×25%~45%」不适用**（原创稿无源长）。**篇幅听 Step 0 选的形态**：短帖 300–800 / 中篇 1500–2500 / 长文 3000+；用户选"结构化笔记"时按模板自己的密度走，不硬凑字数。
4. **「禁止编造」红线不仅适用，而且更严**：素材表里没有的数字，一个都不许出现。
5. **模板里所有以「原文」为主语的条款，一律读作「调研信源」**：自测三问的「须能在原文找到依据」= 能在素材表某行找到依据；思维模型自检的「原文证据句」= 信源原话（官方 doc 的引文优先）。原创稿确实没有可考依据的自测题，整块省略，不硬编。
6. **术语卡模块从「可选」升级为「建议必写」**：Agent 自己是作者，最容易默认用户已经懂（实测写技术选题时，mock/stub、契约、p95、幂等等词会成堆冒出来却没解释）。凡专业性选题，首次出现的术语必须附大白话解释——这一条是踩过坑加的。

其余条款（标题层级、禁止一级标题、禁止话题标签行、末尾 `【核心主题词】` 行、表格化、质量自检红线）**原样遵守**，不要改。

### 3.5 交稿前自检

- 用的哪个模板？在回复里**一句话说明理由**（"选 roundup，因为你要在 A/B/C 之间选"）。
- 关键数据是否都能跳回素材表某一行？
- 有没有为了"模板结构完整"硬凑的模块？有就删（模板明确允许去水分）。
- **维度查全（踩过坑）**：概念型选题常有多个正交分类维度，容易只讲了一个就把标题当讲完了。写前先列该主题的分类维度清单，逐个确认有没有落到**独立小节**。**反例**：讲"压测分类"只给了负载/压力/浸泡（力度维度），漏了接口型/场景型（对象维度）。
- **答疑里的关键区分点必须落成独立小节**，不要塞进别的节里当一句话带过——压成一句话等于没写，用户会回来问。

## Step 4 · 先看稿还是先落盘（2026-09-15 实跑加的开关）

用户说「先不要落盘 / 我先看看质量 / 先给我看稿」时：**Step 3 结束后停在这里，正文直接输出到对话里，不写 JSON、不跑 persist_summary**。并在末尾问一句是否落盘、落哪个目录。

不要因为流水线写到了 Step 4 就自作主张归档——用户要看质量，说明还没认可这份稿子，落盘等于把未过审的内容写进库里（事后要删）。

用户没说"先别落盘"时，才按下面正常归档：

工作目录：`$BLOG_ARTICLE_SKILL_DIR`

1. 写 JSON 文件，字段（`note_type` 必填，值 = Step 3.2 选中的 key）：

```json
{
  "summarized_content": "<笔记正文>",
  "folder": "【我的总结】/<主题>",
  "original_url": "",
  "original_title": "<标题>",
  "author": "",
  "publish_time": 0,
  "note_type": "roundup"
}
```

⚠️ 字段名是 `original_url` / `original_title`（不是 `url` / `title`）。无来源链接时填空串；`author` 填用户指定的名字，无则空串。

2. 执行 `python scripts/persist_summary.py <json> --obsidian`   # 外部依赖：该脚本位于 $BLOG_ARTICLE_SKILL_DIR，不在本仓库
   （自动去重闸门 + 质量门禁 + 注入标签）

⚠️ **长门槛（必看，2026-09-15 实踩）**：机械门禁按模板字数区间拦截——`structured` 区间 1500～5000，超过 `上限×150%` 直接拒绝落盘。用户选型为「长文 3000+」的原创稿必然触发（实测 23320 字被拦：`VERIFIER_FAILED: 字数超出 structured 模板硬上限`）。
**解法（脚本原生支持，无需改代码）**：JSON 里加 `"max_words": <目标字数>` 覆盖上限（判据换成 `count > max_words × 1.5`）。原创长文一般给 26000 足够。**不要为了过门禁去砍内容**——用户要的就是长文。

无 url 的原创稿去重不可靠，落盘前先看目标目录有无同名标题；重复就换标题或加 `--force` 前先问用户。

**落点别搞错**：真实落点是 `$OBSIDIAN_VAULT`（本机 Obsidian 库）；`$BLOG_ARTICLE_SKILL_DIR/notes/` 只是**暂存区**，不是最终归档位置。

## Step 5 · 收尾

汇报四件事：落盘路径、**用的哪个模板及理由**、一手信源条数、仍未解决的疑问。
本轮跑过 agent-reach 的话，顺手 `agent-reach check-update`，有新版在汇报末尾附一句提示。

## 反模式

- **没问受众和形态就开写**（产出必然不对路）。
- **自己发明笔记结构**——9 个模板是单一真源，嫌不合适就选 `general`，不要另起炉灶。
- **凭记忆复述模板 prompt**（6000+ 字符，必须命令取全文）。
- 把模板里"忠于原文"套到原创稿上（没有单一原文，口径是忠于信源）。
- 还没调研就动笔（产出必然是空话）。
- 把 agent-reach 抓来的自媒体观点当事实写。
- 用模板项目的"总结"路径处理原创稿——它是为已有素材设计的。
- 一上来发一堆问题轰炸用户（Step 0 三个问就够）。
