## 1. 目标与边界

**定位重构**：我们不生产「散落的单篇总结」，而是**为下游 agent 编译知识层**。对应到 Brain 的框架，我们自己就是那个 **Dream**（把源持续整理成 wiki），产物应是 wiki 而非平铺笔记。

两条方法论各管一段，共同构成本计划：

- **writing-studio 四步**管「**一篇怎么生对**」：提取 → 结构化 → 成文 → 验证/修正。落在**生成流程**。
- **Brain** 管「**多篇怎么组织成可导航的知识**」：三层 + 索引 + 链接 + 后台编译。落在**库的形态**。

**做**：生成流程补提取与修订环节；库补 L0/L2 层与索引页；跨项目字段契约；评估集。
**不做**：去 AI 味的语感注入改写轮（我们是笔记，且润色会丢限定词）；平台字数口径与钩子豁免；Git 版本化（先不动）；全库重写。
**不改写作台项目的生产代码**，只提出字段契约建议；不更换模型、不新增付费查证。

| 2000–5000 | 184 | **0.887** | **5.4%** |
| 5000–10000 | 125 | 0.782 | 18.4% |
| 10000–20000 | 48 | 0.733 | 22.9% |

**1298 条中 815 条（63%）源锚点 < `MIN_ANCHORS`，锚点判据不适用。** 我们唯一的保留度量化指标只覆盖 37% 语料。
结论：长源分治/先提取后成文有数据支撑，但**只对 >1 万字**；<5000 字段现状已够（5.4%），不必动。

### 2.2 下游依赖：我们的库就是 writing-studio 的 KB

- `KB_ROOT` 直指 `D:/Code/Obsidian/obsidian-path/AI 总结笔记`（= 本项目真实阅读库）。
- 下游从一篇 md 只取 5 个字段：`title` / `path` / `sourceType` / `publishedAt` / `excerpt`，**检索单元是段落**（`splitKnowledgePassages`），不是整篇。
- `classifySource` 按**路径子串**判类型：含「【监控】」→「对标」。实测库存：监控 **1445** / 我的总结 **867** / 生财有术 21 → **62% 库存权重 0.7**（`TYPE_WEIGHT` 原创 1.0 / 其他 0.85 / 对标 0.7）。
- 「对标」不只是权重：`draftPrompt.ts` 明令「只可借鉴观点/角度/结构，**绝不照搬原句**」；`kbMerge.ts` 有「对标最多 N 篇」防洗稿红线，超限截断。
- **`publishedAt` 在本地 md 分支恒为 `""`**，不解析 frontmatter —— 但我们的 frontmatter 里已有 `published_at` / `source_url` / `freshness` / `title`。管道接上、阀门没开。

**分类语义错配（反驳「对标」的核心论据）**：Brain 官方把记忆分成两种 —— **Memory** 存偏好与兴趣（让系统"认识你"），**Brain** 存项目/人/文档/决策/open loops 的关系图（**工作上下文**）。按这个划分，我们的笔记库提供的是 **Brain（工作上下文与证据）**，不是 Memory（用户偏好）。而下游把「【监控】」判为「对标」（= 别人的、竞品的材料），在 Brain 框架下是错的：原始层不是"低价值的别人东西"，而是**证据层**，其价值在可追溯（citation），不在权重高低。
→ 建议下游按**抽象层级**（原始/片段/整合）分类，而非按「原创/对标」的你我之分。

**下游加载机制**：Brain 实测「全量拷贝太贵、远程读慢 400–500 倍」，故用**工作集 + memory agent**（先拷一批，缺了再按需成批拉）。下游现为全量索引（`kb-index.json` 近 100MB、首次 bootstrap 29.1s、进程常驻 1.2GB），正是 Brain 描述的反面场景。属下游侧优化，本计划只登记不实施。

## 3. 目标形态

### 3.1 三层结构（对照 Brain 的 `knowledge/` `notes/` `sessions/`）

| 层 | 对应 Brain | 现状 | 作用 |
|---|---|---|---|
| **L0 原始层** | `sessions/` | `_raw_*.md` 已存在，但在项目 `notes/` 内、**下游拿不到** | 可追溯：出问题能查原文 |
| **L1 片段层** | `notes/` | **2310 篇，现状全部家当** | 单源总结，回答 single-hop 问题 |
| **L2 整合层** | `knowledge/` | **【我的总结】867 篇已是雏形，但非 wiki 形态**（详见 §3.5） | 跨源主题页，回答需跨周月拼证据的问题 |
| **索引页** | 总目录 | **缺失** | 让下游「知道有什么可查」 |

Brain 原话：三层「deliberately redundant」—— 简单问题在 `/notes` 搜关键词就够，`/knowledge` 用于需跨会话拼证据的问题。**问题难度决定取哪层。**

### 3.2 链接（Brain 用 `[[page]]` 横向 + `[cite:N]` 向下）

- **向下（溯源）**：我们已有来源链接（formatter 权威追加）+ `evidence.py` 的行号级校验结果，但行号**只在校验时报一次告就丢**，未持久化进页面。
- **横向（相关）**：完全缺失。现靠标签隐式表达，下游不认。Obsidian 原生支持 `[[双链]]`，但混入正文会污染下游 bigram 分词，**要放独立关系区，不散在段落里**。

### 3.3 生成流程四步落地规格

判据分三级，是贯穿本计划的总原则（源于我们自己的教训：括号信号假阳性 63.2%、字数比例带被证伪、形态信号实测不触发）：

| 级别 | 判据类型 | 处置 |
|---|---|---|
| **硬拦** | 机械可判、误报低 | 直接拦 + 重交 |
| **报告项** | 只能模型判 | **不计分、不拦**，只观察；有效再升级 |
| **软信号** | 存疑、未标定 | 只提示，不参与判定 |

**第 0 步 源**：不改。`§七之二` ASR 修正规则已覆盖。只补两个给下游步骤用的产物：源长度测量（决定单段/分治）、长源切片。

**第 1 步 提取**（新增）
- 触发：源长 >10000 字才启用模型提取；<5000 字只跑机械（数据见 §2.1）。
- 机械层（零成本）：复用 `_anchor_specs`，产出锚点清单。
- 模型层（1 次低温调用）：四分类抽取 —— 具体事实/数字/引述、作者亲历、判断推断、假设示例，外加论点清单，**每条必须带源位置**。
- **清单是检查表，不是大纲**。当大纲用会驱动编造（`content_signals.py` 注释已记此坑）。
- 验收：每条必须能在源里原样命中，命中不了丢弃（机械可验）。
- 判据级别：**先做报告项**。

**第 2 步 结构化**
- 把 `SECTION_CONTRACTS.required`（无条件）拆出 `conditional`（条件必备），条件由**机械信号**判定（对比数字组数、反例关键词、时间线密度）。
- 解决「源不支持的模块驱动编造」。属模板改动（冻结已于 2026-10-18 解除，见 §5），可直接设计实施。

**第 3 步 成文**
- 短源（<5000）：one-shot 不动。
- 长源（>10000）：**先列要点、再成文**（两阶段）。不直接上「分块总结→合并」——后者要解决合并一致性，成本更高，先验证两阶段够不够。

**第 4 步 验证与修正**（完整是四件事，不是一句「过检查」）
1. **判定**：确定性检查（已有：H1/链接/URL/字数/结构/锚点召回/照搬）+ 语义检查（`review_fulltext`，默认关）
   ⚠️ **稿件不丢**（方法论三大底层认知之一，与现状直接冲突）：现流程是「门禁不过 → 不落盘 → 子 Agent 重写，两次仍失败则跳过」，**稿会丢**。应改为**先落盘留档（标记未通过）再判定**，判定与修正都在已有稿件上进行 —— 与 Brain 的 staged output tree 同一原则：先有暂存物，再谈改不改。T7 承担此改动。
2. **定向修订**：把**上一轮全文 + 分数 + 具体问题**一起给模型，低温，只改指出的问题。现状 `retry:true` 是整篇重写，应改为定向修订（writing-studio：「保留上一轮完整输出…比新开对话重述全套要求稳」）
3. **边界校验（信息守恒）**：不许新增（每个实词要能在源指出出处）、不许删减（观点/结论/限定词）、**不许改语气强度**（含反向：把确定改 hedge 同样违规）
4. **先比后换**：修正稿不自动替换，过门槛 + A/B 比较后才换

### 3.4 决策点（简化后仅第 1 项需拍板）

状态总览：

1. **方向（服务下游 agent）—— 仍需拍板**
2. **L0 处置 —— 已降级**：先验证下游是否支持多 source；支持则 T14 自动执行，不支持才需回来拍
3. **L2 —— 已降级**：按既定策略先跑 T1 探针，现在不需拍

以下每项给出选项、代价与推荐，不做无依据的二选一。

**决策点 1 · 是否把「服务下游 agent」定为项目目标？**
前提：下游依赖已是**既成事实**（§2.2 `KB_ROOT` 直指本库），不是待验证的假设。故这不是「做不做」的选择，而是**承不承认这个事实并据此设计**。
- **选「是」**：投 T8–T12（索引/链接/暂存受控替换/后台循环）。代价最大，部分任务需排在评估解冻后。
- **选「否」**：维持散落笔记。省下阶段 2/3；代价是下游继续低质量使用（62% 库存降级），而我们继续在 63% 盲区里改。
- 推荐：**是**。依赖关系已经发生，主动适配优于被动承受；且 T1 探针可先花小钱验证。

**决策点 2 · L0 原始源进不进 vault？**
- **进 vault**：下游可追溯到原文并核实。代价：库体积翻倍级增长、检索信噪比下降（检索会命中大量原文而非笔记）、索引耗时增加。
- **不进 vault**：库干净、检索快。代价：下游无法核实，笔记错就是错。
- **第三条路**：`_raw_` **不进 vault**，但在 L1 笔记内保留**可定位指针**（源链接 + 源行号），需要时按指针回溯。这正是 Brain `[cite:N]` 的做法 —— **引用是指针，不是复制**。
  ⚠️ 第三条的收益此前被高估：`_raw_` 在项目 `notes/` 内，而下游 `KB_ROOT` 指向 vault，**指针对下游 agent 是死链** —— 它顺着指针取不到原文。所以第三条只对人可追溯，**对 agent 不可核实**。而 Brain 的 `sessions/` 层就在 `memory/` 树内、agent 可直接访问。
- **第四条路（新，推荐）**：原文**不进 vault 主树**，另建**源快照库**并作为**下游的第二个 KB source** 挂载（下游 `kb-sources.json` 已支持多来源，现只挂了 `local-default` 一个）。
  - 常规检索只走笔记库 → **不污染信噪比**
  - 需核实时走第二个 source 检索原文 → **agent 可真正追溯**
  - 不改动下游代码，只加一条 source 配置
- 推荐：**第四条路**。它是唯一同时满足「agent 可核实」与「检索不污染」的选项，且改动最小。由 T10 承担（指针 + 第二 source 挂载）。

**决策点 3 · L2 跨源整合页做不做？**
- **做**：能回答需跨多源整合的问题（Brain 数据中增益最大的部分）。代价最贵，且依赖 T10 横向链接与 L1 自身质量。
- **不做**：省下最大成本。代价：下游只能拿到单篇片段，无法回答「关于某个主题，我积累的全部认识是什么」。
- 推荐：**先不做，先跑 T1 探针**。索引页是「目录」，L2 是「内容」；目录若无效，内容大概率也无效。T1 结果出来再定。

### 3.5 存量实情：库是两半，处境完全不同

2026-10-18 实测：

| 部分 | 篇数 | 性质 | 下游判定 |
|---|---|---|---|
| 【我的总结】 | 867 | **整合型笔记**（文件名是章节/主题名，如「一、Agent与Harness」），**无单一外部源** | 原创，权重 **1.0** |
| 【监控】 | 1445 | 单源总结，文件名 = 源标题 | 对标，权重 **0.7** |
| 生财有术 | 21 | 单源总结 | 其他，权重 0.85 |

两条由此而来的修正：

1. **L2 不是从零建** —— 【我的总结】那 867 篇本身就是整合产物，**是 L2 的雏形**。缺的不是「整合内容」，而是 wiki 形态（链接、引用、版本、可导航）。
2. **配对率**：源与笔记按文件名几乎无法直接配对（精确 **0%**、模糊 0.85 仅 **14.4%**，因命名规则差异 —— 笔记带日期前缀、双方均截断 80 字符）。经 registry + BV 号 + 标题相似（0.9）路径可配 **1298** 条，占「有外部源的 1466 篇」的 **88.5%**。

→ 对 T10：约 11.5% 的有源笔记配不上源，无法建立引用指针；【我的总结】本就无单源，不适用引用指针。
→ 对 T11：L2 的低成本起步**不是**「从 1445 篇【监控】聚类生成主题页」，而是**先规范现有 867 篇**。

### 3.6 源的位置信息（T10 前提）

视频源的 ASR 转录稿为**纯文本逐行、不含时间戳**（实测样本无 `[MM:SS]` 标记），故引用指针只能用**源文本行号**，不能用时间戳；文章源可用段落 / 行号。
现 `evidence.py` 只记**笔记侧**行号（`note.line_start`），**无源侧位置** —— T10 需补上源侧行号。

### 3.7 Brain 框架的简化版（我们的适配）

**一条分界线**：Brain 是「**持续演进的记忆**」—— 内容会自己变（用户偏好更新、项目进展、信息过时），所以它整套机制都在处理「变化」。我们是「**静态知识的组织**」—— 源一旦抓取就不会自己变，笔记生成即定型。
→ **凡是为处理「变化」而存在的机制，我们一律不需要。**

**砍掉的（含理由）**：

| Brain 机制 | 处置 | 理由 |
|---|---|---|
| Dream 常驻循环（Orient / Summarize / Attach / Update） | **砍常驻**；Summarize + Attach 保留为生成时的一次性动作 | 源是静态的，不会随时间变化 |
| 「update 已变 / mark stale」 | **砍** | 我们的笔记不会过时 |
| 工作集 + memory agent | **砍** | 我们没有临时沙箱问题，下游直接读 vault |
| Git 版本历史 | **砍**（同 §7） | 库非 git；我们的更新是「方法改进」驱动的批处理，非逐次演进 |
| 条目级 corrections 回流 | **砍 · T12 撤销** | 我们总结的是第三方内容，**没有「用户纠正事实」这回事**；人工改的是 ASR 错字与表达，不具可推广性。系统级根因台账保留 |
| 合成人格评估（640 题 / 44 persona） | **换成真实语料评估集** | 我们有 1298 对真实源/笔记配对，比合成数据更直接 |
| Memory / Brain 之分 | **砍** | 我们没有 Memory（用户偏好）层，只有工作上下文一层 |
| staged output tree（整体更新图） | **简化为单篇暂存** | 我们的笔记相互独立，「整体性」只在 L2 才有意义 |
| Orient 的删除日志 / 常设指令 | **砍** | 我们没有主动删除流程 |

**保留并简化（这才是我们要的）**：

| Brain 机制 | 我们的简化版 |
|---|---|
| 三层 sessions / notes / knowledge | **两层 + 外部源库**：L1 单源总结（1466）／L2 整合页（867，**已有待规范**）／源快照库独立存放、不进 vault |
| 总目录 | **索引页**（最便宜，T1 探针） |
| `[cite:N]` 引用链接 | **源行号指针**（ASR 无时间戳，只能用行号） |
| `[[page]]` 横向链接 | **按标签自动生成**，不人工维护 |
| 页「单看一页也能看懂」 | **段落自包含**（我们的检索单元是段落，比页更小） |
| 暂存 + 双验证 + 受控同步 | **保留**，简化为单篇级（T8） |
| 「也可以选择不改」 | **保留**（T13） |
| 后台离线、不占前台 | **保留**，简化为落盘后抽检，非常驻（T7） |

**简化后的形态**：

- **结构**：L1（1466）＋ L2（867，已有待规范）＋ 索引页 ＋ 外部源快照库
- **连接**：引用指针（→ 源）＋ 相关链接（自动生成）
- **流程**：提取 → 成文 → 暂存 → 验证 → 受控落盘（**一次性**）
- **无常驻循环**：知识不会自己变；需要更新时走批量重做（T8 / T13）

一句话：**我们不需要「会成长的记忆」，需要的是「被组织好的静态知识」。**

### 3.8 索引页与目录设计

**库目录保持不动**：现有一级目录【我的总结】/【监控】/ 生财有术 /【待归类】已对应 L2 / L1 划分，且下游 `classifySource` 按路径子串判定类型，改动需同步下游代码 → 不动。

**索引页新增，两级**：

```
vault/
  00-总目录.md            ← 入口：列出各领域 → 领域索引页
  _index/<领域>.md        ← 每领域一页，列出该领域全部笔记
```

**每行格式（核心约束：一行自包含）**：

```
- [《笔记标题》](../相对路径) — 一句话说清这篇讲什么｜来源类型｜2026-09
```

设计约束全部来自下游的实际行为，不是凭空定的：

| 约束 | 依据 |
|---|---|
| 必须有 H1 | 下游 `titleOf` 取正文首个 `# 标题`，无 H1 则退化为「首行前 60 字」 |
| **每行自包含** | 下游按段落切片，含糊的行切出来就是噪音 |
| 每行带链接 | agent 可跳转（对应 Brain 的「目录 → 页」） |
| 每行带日期 | Brain 官方数据中 temporal reasoning +8.6pp，是增益第二大项 |
| 按领域分文件 | 单页 2333 行过长；分领域后每页聚焦、命中更准 |

分类依据优先用**现有目录 / 标签**（机械可拼），不逐篇过模型 —— 这是 T1 要验证的目标。

### 3.9 下游如何使用（能力边界，须诚实）

**关键落差**：Brain 的下游是**导航型 agent**（会 cat / grep / 点链接 / 先看目录再决策）；writing-studio 的下游是**检索型消费者**（Orama 全量索引 → 段落命中）。**我们不能直接把"导航型"设计套给"检索型"消费者。**

因此本计划提供的是「**可按难度选层的素材**」，**不是自动的导航行为**：

- **短期（现状 + 本次改动）**：下游继续 L1 / L2 混检，靠 `sourceType` 权重区分 —— L2 整合页（【我的总结】867 篇，权重 1.0）优先，L1 单源总结（1445 篇，权重 0.7）作证据层。
- **中期（T1 后）**：索引页让「关于 X 我有哪些积累」这类问题能命中目录行，而不只是碰运气命中某篇段落。
- **长期（非本计划工作）**：若要让 agent 自动「先看目录 → 按难度选层 → 顺链接核实」，需下游实现导航层。它现有的是**人工 scope 选择**（`kbSourceIds` / `kbScopes` 三级目录），即人可手动选层、agent 不能自动选。

**用 L1 还是 L2 —— 两者都用，用途不同**：

| 需求 | 取哪层 | 理由 |
|---|---|---|
| 要事实 / 证据 / 可核实 | **L1**（单源总结） | 有引用指针可追溯到源 |
| 要综合认识 | **L2**（整合页，867 篇已在） | 跨源整合的结论 |

**待办（归入 T2）**：建议下游把 L1 的 `sourceType` 从「对标」改为更准确的语义 —— 按 Brain 框架，L1 是**证据层**而非「别人的竞品材料」，现标签会连带触发「禁止引用原句 + 限篇数」两条硬约束（§2.2）。

## 4. 风格层：目标是机器可读性，不是人味

风格问题分两类，我们要的只是第二类：

| 类别 | 例子 | 要不要 |
|---|---|---|
| 人味类 | 破折号密度、翻案腔、长短句参差 | ❌ 不在意；且润色会丢限定词 |
| **机器可读性类** | 段落悬空指代、超长句、相邻段重复 | ✅ **功能性缺陷** |

第二类是下游能不能用的问题：段落写「这个方法/如上所述」→ 下游按段落检索拿到孤立片段 → 直接变残缺事实；单句 >140 字 → 切片一断语义就残；相邻段重复 → 白占 context。

**走生成端预防，不建独立改写轮**（writing-studio 三道防线第一道即「生成端预防，零 token」，且改写最容易丢限定词）。
前提是先测命中率：全库扫段首悬空指代（正则可判），高才加约束，低就是在解决不存在的问题。

## 11. 收益重估（用户质疑后）

> 质疑原文：「对下游没帮助的话，我们引入 Brain 框架感觉意义就不大了，我们自身项目需要？」

### 11.1 先修正 §3.9 的一处保守判断

§3.9 说索引页对检索型下游只有「中期」价值，**这是说轻了**。索引页对检索型下游有**真实且直接**的价值，只是机制与 Brain 不同：

- 逐篇检索会漏（不同笔记措辞不同），而索引页按领域聚拢了全部笔记的一句话摘要 → **一次命中拿到该领域清单**，是检索的**召回补丁**
- 索引行是高信息密度浓缩，命中它 agent 先拿概览、需要再进详情 → 这正是 Brain 实测 **token −15%** 的机制

所以索引页不是「导航的廉价替代品」，而是**检索型消费者的召回补丁 + 上下文压缩器**。

### 11.2 但质疑本身成立：收益必须分两列算

| T7 稿件不丢 + 后台异步 | **中高** | 无 |
| 第 1 步提取（含 T0 / T6） | **高**（提升保留度） | 间接 |
| T9 条件必备结构 | 中（防编造） | 间接 |
