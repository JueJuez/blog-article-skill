## 各缺陷详述

以下症状与候选方案保留原盘点记录；实际实施范围以本文前述已确认方向和开发计划为准，未采纳的全量化、门禁升级及逐篇评分建议不得直接执行。

### D1 · 普通长度源信息覆盖率无保障
- **症状**：源 1k 字 → 笔记几百字、丢 1–2 个观点/知识点，全程无事前提取、无事后覆盖对账。系统靠 prompt 里"覆盖优先铁律"靠模型自觉，模型偷懒即静默丢。
- **代码事实**：`summarize_content` 是"模板 + 整篇源文"一次性 `generate`；`verify_note_mechanical` 两道字数线都是极端护栏，无"信息覆盖率"判据。
- **优化方向**：提取轮（先结构化抽"观点/知识点/表格/图注"，再总结逐条对账"每条都有落点"），且从"仅 >10k 源"扩到全长度源。见 D3。

### D1 现状（2026-10-26，S2 实测）
- 试验：`notes/_meta/eval/20261026-thin-checklist/`。5 篇 2k–10k（3 文章 + 2 视频）配对，固定必留清单 58 条（机检 58/58），两臂只差 799 字薄清单块。
- 结果：control 57/58 hit（98.3%）、treatment 56/58（96.6%）；失真 2→4、无源 1→2、成稿 −13.9%。**没有任何一篇出现 treatment 独有落点**。
- 归因：必留清单是 items 级，one-shot 已能保住；真实失败模式（整段论证/反例丢失、数字归属错置、ASR 处补精度）不在 items 级别上，加清单只与正文争抢同一次输出预算。
- 结论：薄清单不推广，`NOTE_THIN_CHECKLIST=0`；**D1 本身的覆盖率缺口未解决**，要动只能换机制（如事后对账升级/分段抽取），不在本轮范围。

### D2 现状（2026-10-26，S3 第一阶段）
- **已做**：抓取时记台账（`有图/装饰图/已读/取不到图片信息`），派单只在有缺口时加一行
  「源含 N 张图未读，不得凭 alt 编造」；审核元数据带 `image_state`（**不进 reasons**，防抽样率被放大）。
  实测小样本：2 张流程图恢复出分支与回边，纯文本抽取下这部分 100% 丢失；1 项误读（漏终态）被独立核对抓出。
- **仍缺**：主源 scys / 飞书走 CDP 文本通道，状态只能是 `unknown_no_html`——**数不出图**。
  要数就得在 CDP 抓取时取 DOM 再跑 `extract_images`，属抓取层改动。
- **刻意不做**：批量 OCR、自动识图、按图数量设门禁；"重要图"目前靠人挑。
- 证据：`notes/_meta/eval/20261026-image-gaps/REPORT.md`；机制见 PIPELINES §3.10。

### D2 · 图片类知识载体零信号
- **症状**：XMind、鱼骨图、信息图、截图等"以图为主要知识载体"的内容，只要源里是图片形式，整个丢失——不是压缩，是零信号。
- **代码事实**：`fetch.py` 走 trafilatura 只抽文本，不做 OCR；模型拿不到图，只能看到图片旁的 alt/caption 文字（若有）。
- **优化方向**：评估 OCR / 多模态抽取通道的成本与收益，决定哪些载体值得抽、抽到什么粒度。与 D1/D3 独立——提取轮救不了纯图载体。

### D3 · 提取轮机制残缺（A4 清单）
- **症状**：真·提取轮（独立预抽取）生产链路不存在；现有"清单"只在源 >10k 注入，且是同一模型在同一次输出里"先列清单再成文"，事后剥离校验但**不拦盘、不触发重交**；2k–10k 无任何清单。
- **代码事实**：`extract_checklist.py` `EXTRACT_MIN_CHARS=10000`；`render_extraction_rules` 对 2k–10k 返回空串；模块 docstring 明确"报告项、不计分、不拦盘、不触发重交"。
- **优化方向**：① 把清单触发从 >10k 扩展到全长度源（含 2k–10k，甚至 <2k 也带薄清单）；② 把 `reconcile()` 产出的 `unmatched`（清单条目没进成文）从"观察项"升级为可配置门禁（软抽检 or 硬拦截）。
- **重做侧影响**：`resum_save_batch.py` 已将 A4 清单内化（`_process_checklist`）到落盘前，但触发仍受 `EXTRACT_MIN_CHARS=10000` 约束——2k–10k 的重做稿同样无覆盖对账。修 D3 即同时覆盖增量与重做两侧。

### D4 · 成稿后真检默认不发生
- **症状**：用户直觉"机械+内容门禁就是复审"——其实不是。门禁是落盘前拦截；落盘后只有异步复审队列，且默认只触发式入队（review_flags 非空或 15% 抽样），**入队不调 AI、不消费就不审**；独立语义复审 `NOTE_QUALITY_GATE` 默认关。
- **代码事实**：`templates.py:1110` `QUALITY_GATE_ENABLED = os.environ.get("NOTE_QUALITY_GATE","0")=="1"`（默认关）；`shared/async_review.py` 只 `maybe_enqueue`，消费端 `scripts/run_async_review.py` 需显式跑。
- **优化方向**：让复审真正发生——要么接 `run_async_review` 消费端（落盘后批量审），要么开 `NOTE_QUALITY_GATE`（落盘前第二遍 AI 把关、拦盘）。优先对覆盖缺失项（D1/D3 的 `unmatched`）做复检。
- **S1 现状（2026-10-26）**：消费端已升级为「有界选单 → 派单 → 独立回收 → 批次报告」，入口见 [PIPELINES §3.2.1](../docs/PIPELINES.md)。首批真实批次 `arv-20261026-194355` 4 篇全部判 fail（73/80/75/87 分），证明「审了」确有产出；但**它仍然不会自己发生**——`NOTE_QUALITY_GATE` 默认仍关，队列仍要在监控/批次收尾时由编排会话显式跑。故 D4 只算「有了低成本的发生路径」，不算「默认发生」。

### D5 · 无生产内量化覆盖率指标
- **症状**：任何改动只能"看起来更好"，没有每篇可量的保留率。硬锚点判据在全量语料只覆盖约 37%（历史结论），靠它估覆盖率会高估。
- **代码事实**：评估集 `build_eval_set`（30 篇分层抽样固定基线）与对照轮 `build_round` 都是离线调参台，不在生产跑；`content_signals` 的锚点召回 `<60%` 仅"源锚点≥4 条"才适用。
- **优化方向**：把评估集/对照轮思路接到生产抽样，给每篇一个可量保留率，作为 D1/D3 修复后的验收尺。
- **S1 现状（2026-10-26）**：已有**批次级**最小统计（处理量 / 真错 / 误报 / 未确认 / 修订 / 轮次与消耗），分母分身份、未知写 unknown；首批实测：22 条 findings → 真错 5、误报 3、未确认 14，误报率 3/8=38%（只算已裁定）。**仍没有逐篇语义覆盖率**，报告里已明确禁止把机械命中率包装成分数。

### D6 · 表格/图表重生无数字对齐校验
- **症状**：表格→Markdown、图表→`chart` 代码块、结构图→mermaid，全靠 prompt 指令让模型"据文字数字重画"，没有校验"重生图里的数字与源一致"。
- **代码事实**：`QUALITY_DISCIPLINE_RULES` 的 chart/mermaid 节要求模型重画；`fetch.py` 抽文本后由模型重建，无对账。
- **优化方向**：对重生图里的源数字做对齐校验，复用 `extract_checklist` 的 token 命中思路（图内数字/专名应在源 token 中找得到）。

### D7 · 必要性判定救不了"信息丢失型旧稿"
- **2026-10-26 实测（S1 批次）**：5 条经独立复审核实的语义真错（整段论证/反例丢失、数字归属、ASR 补精度）中，
  对其中 3 篇跑 `check_resum_necessity.py` 单片判定 → **全部 keep「无确定性缺陷」**。
  即：语义遗漏在 hard 集合里不存在，这类旧稿永远进不了重做队列（与 D1 同源逆向）。

- **症状**：重做链路第一道护栏 `check_resum_necessity` 判 `keep`/`redo` 只用 hard 集（锚点召回/结构缺失/照搬/证据确定性缺陷）。一篇旧稿"源 1k 字→笔记几百字、丢了 2 个观点"这种纯信息压缩损失，**没有任何 hard 信号**，于是被判 `keep`（选择不改），永远不进重做队列。
- **代码事实**：`shared/note_audit.py` `necessity_of` 取 `classify_content_flags(flags)["hard"]` + 证据 `block`；形态/覆盖率信号在 `soft` 里、不构成 redo 理由（`check_resum_necessity.py` 注释明确"形态信号不构成重做理由"）。2026-10-18 全量：1396 候选 → redo 391 / keep 1005。
- **与 D1 的关系**：D1 是"防止**新稿**丢信息"，D7 是"**旧稿**已丢信息却不被识别为该重做"——同一根因（覆盖率无判据）的两种表现。修复 D1 的提取轮+覆盖对账可复用到必要性判定：把"压缩比/锚点漏失/清单 unmatched"纳入 redo 理由。

### D10 · 该画图时没画（2026-10-26 新增，候选 S4）
- **怎么发现的**：用户质询「真的需要图？还是文字不够？还是该生图没生图」，用库内数据逐个验，第三条成立。
- **证据**：2459 篇里 mermaid 6.8% / chart 3.8% / 全篇无图 90.7%；540 个结构类小节中箭头≥6 的 42 个，
  其中 **33 篇整篇无图**；周复盘 25 篇仅 2 篇有图，其「逻辑框架」小节 13–26 个箭头全是文字链条。
- **不是 D6**：D6 是「重画出来的图数字没校验」；D10 是「根本没画」。两者会叠加——先敢画，才谈得上校验。
- **反向证据**：S1 那 22 条回源核实的缺陷里 0 条是「源有图未读」→ 当前第一缺口不在「读源图」。
- **状态**：候选方案与验证设计写在计划 §6，**未立项、未改 prompt**；动之前要过 5 篇配对验证。

### D9 · 重做元数据不受 T8 保护（2026-10-26 新增）
- **症状**：受控替换只数内容缺陷（锚点/结构/照搬/证据），信息块退化（来源链接变「【无来源链接】」、

### D8 · 受控替换只防变差、不追求变好
- **症状**：第二道护栏 `controlled_replace` 是"候选稿与旧稿比确定性缺陷数，明确更少才替换，相等/更差保留旧稿"。于是新稿可能在信息组织、覆盖率、可读性上明显更好，但只要缺陷数 = 旧稿（往往都是 0），就判 `no_gain` 保留旧稿——**一个无缺陷的旧稿永远不会被更优的新稿取代**，除非它恰好踩中某条 hard 缺陷。
- **代码事实**：`shared/controlled_replace.py` `decide`：`d_new < d_old`→replace；`d_new > d_old`→keep；相等→`no_gain`（keep）。`--force` 才是无条件替换（逃生舱）。判据零新增（与 T13 同一 hard 集）。
- **取舍与优化方向**：这是刻意的（Brain"也可以选择不改"），代价是"重做只能修坏稿、不能升级好稿"。若要升级好稿，需在缺陷数相等时引入质量增益维度（覆盖率对齐/评估集分/对照轮判分），明确"新稿更优"才换；否则保留现状（保守优先）。此改动会动 T8 的保守哲学，需先与用户确认再排期。
